Customers / Operators tab · Pending invite card

Admin invite — card states

Five live states of PendingInviteCard, each with a different primary action. The card's job is to make the next likely action obvious without users having to think about Resend vs. Regenerate. Communication failures resolve cheaply (resend); credential failures resolve expensively (regenerate). The two paths must not collapse into one button.

Primary action by state

Same data shape; different recommended action surfaced as the biggest button.

The link is no longer valid. Anyone who tries to use it will see "link expired". Regenerate to issue a fresh link (auto-emails to the last recipient by default), or cancel to abandon the invitation.
Regenerate is now the only repair path — Resend would mail a dead link, so it's hidden. The follow-up flow auto-prefills the recipient email and pre-arms the Send button in the modal, so the user lands one click away from "fresh link sent to the same person." Cancel invitation stays a ghost to keep the destructive verb low-temperature.
Should "View link" become "Send email"?
No. The rename collapses two different jobs (inspect / deliver) into one. Instead, keep both verbs but let the card's primary slot rotate based on state. "Resend email" appears as primary only when it's actually the most likely next step (state ②), and the View details / Copy link path is never lost.
How Regenerate behaves across states
Ghost in ①②④ (avoid unnecessary token churn) → secondary in ③ (escalation hint) → primary in ⑤ (only valid repair). Every state except ⑤ surfaces a confirm dialog listing who will lose access to the old token, so the destructive nature stays visible.
