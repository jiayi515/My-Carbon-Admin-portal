Carbon Admin Portal · Design spec

Approval workflow

Sensitive operations on a customer's operators — changing an Email and granting / transferring the Admin role — must pass a two-person review before they take effect. This document covers the state machine, the new Approval Center, the submitter and reviewer surfaces, and the disposition of the original Admin after a role transfer.

1 · Change Email

Email is the recovery + login credential. After approval, the new email address must verify ownership before the swap takes effect.

2 · Transfer / Grant Admin role

Admin has full billing, fleet and operator permissions. Approval takes effect immediately and atomically (demote + promote in one step).

08 · OPEN QUESTION

What happens to the original Admin after a transfer?

Three reasonable answers. They imply different mental models and different recovery paths. Please pick one — I'll wire the chosen behaviour into the modal.

A · Demote to Operator

Original Admin stays on the customer but loses Admin permissions. Keeps email access, can still log in, can still be promoted again later via another approval.
J Jamie Admin Operator
Pros
  • Matches what users expect from "transfer."
  • No information loss — context for support, audit, hand-off.
  • Reversible: promote again with another approval.
Risks
  • Old Admin still has login access — if compromise was the reason for transfer, remember to revoke separately.

B · Keep as second Admin

Transfer means "add another Admin." Original Admin keeps full permissions; the new Admin gets full permissions too. Customer now has two.
J Jamie Admin + P Priya Admin
Pros
  • Eliminates the "single-Admin gets locked out" failure mode.
  • Two-eye coverage on tenant operations.
Risks
  • Doesn't match the word "Transfer" — relabel to "Grant Admin".
  • Mutual demotion still needs a separate flow.

C · Remove from customer

Original Admin is fully detached. Cannot log into this customer at all afterwards.
J Jamie P Priya Admin
Pros
  • Cleanest answer when the original Admin left the company.
  • One step instead of two.
Risks
  • Destructive — easy to lose audit context.
  • Conflates two distinct intentions (transfer vs. offboard).
Recommendation: A · Demote to Operator. It matches the verb "Transfer", is reversible, and keeps audit context. We can offer B and C as separate actions later (Grant Admin, Remove operator) — they don't need to be folded into Transfer.

09 · GUARDRAILS

Edge cases worth nailing down

Things the design has to behave well in — most are covered by the rules already, listed here so we can sanity-check together.

Submitter ≠ reviewer The same Carbon account can never approve its own submission. The "Approve" button is hidden on those rows. enforced server-side
Target ≠ reviewer If the request targets operator X, then X also cannot approve (even if X is a Carbon Admin in another tenant). defense-in-depth
One pending per operator per type If Change Email is already pending for Maya, the menu item is disabled with tooltip "Pending review — withdraw to submit a new one." avoid duplicates
Always at least one Admin Transfer is allowed; standalone Revoke Admin is blocked when there's only one Admin on the customer. anti-lockout
No emergency bypass By your decision, single-person mode is not allowed. There is no override path — operations team must coordinate two Admins. confirmed in scope
Verification link expiry Email change: link expires in 24h. Resend link action is available to any Admin while the request sits in Awaiting user verify. resendable
Audit retention All four lifecycle events (submit / decide / verify / apply) land in the customer's audit log. Visible in the Customer-detail audit drawer; also exportable. forever
