Customers / Operators tab · Pending invite card

Admin invite — card states v2 · no history

Without a resend counter or "last sent" timestamp, the state machine collapses from five states to three. "Send" and "Resend" become the same verb — the system doesn't know or care whether this is the first send or the fifth. The card just has to answer: "is the link still good, and is there a recipient on file?"

What changed from v1
Dropping email history removes both the data we tracked (resendCount, last-sent timestamp) and any UI built on top of it. Two whole states disappear.
Removed
  • State ① Just sent (depended on "< 5 min ago")
  • State ③ Stalled (depended on resendCount ≥ 3 + escalation banner)
  • "Sent 2× · last 12 min ago" pills on every card
  • Distinct "Resend" verb (now just "Send")
Kept & simplified
  • Active · email on file — primary is Send email
  • Active · link-only — primary is Copy link
  • Expired — primary is Regenerate
  • Confirm dialog before re-sending (replaces the counter as the friction layer)
Primary action by state

3 states. Card derives state from pendingInvite.recipientEmail and expiresAt. No counters required.

One verb covers first-send and resend. Without history, the system can't and shouldn't differentiate — Send email works whether the user is sending for the first time or the fifth. The card shows the recipient as a single editable field (not a log), so the user can also fix a wrong address in place. Regenerate is ghost because in this state it would invalidate a perfectly good token; users only reach for it for security or expiry reasons, not delivery reasons.

Q1 · Customer didn't get it
Click Send email (primary in state 01). Confirm dialog gives a chance to fix the address. Link stays the same.
Q2 · Rename View link?
No. Let the primary slot rotate by state instead. View details remains as a stable secondary so power users can always inspect link/QR.
Q3 · Regenerate behaviour
Ghost in 01 & 02 (avoid token churn) → Primary in 03 (only valid repair). Always shows a confirm dialog naming who'll lose the old token.
